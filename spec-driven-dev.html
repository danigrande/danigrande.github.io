Spec Driven Development

Writing the specification first — then letting AI agents implement it. The method that makes agentic coding reliable instead of chaotic.

Method: BMAD Proven on: GrandeSuite Next Status: Ongoing practice

BMAD Spec-First Traceability Agentic Delivery

AI agents can write code fast. The hard part is making sure they build the right thing — and keep building it as the product evolves. My answer: never let code lead. The spec leads; the agents follow.

Every feature starts as a written requirement with testable acceptance criteria, moves through architecture and design, and only then becomes work an agent can implement — with full traceability from code back to intent.

0 Why This Project

Agentic coding is fantastic for a personal project — you decide on the fly, change direction mid-build, and keep the whole thing in your head. But that way of working is impossible on a team. Software development has always needed structure for a reason: frameworks like Waterfall and Agile, with specifications, QA, and process, exist because coordination doesn't happen by accident.

Frameworks like BMAD caught my attention because they make that structure AI-native. With agents playing the different roles on a team — analyst, architect, designer, engineer, test architect — you can generate specifications and user stories, and even run an Agile debate without a room full of people.

As a PM, preparing user stories and running Agile ceremonies consumed about 80% of my time. If software could accelerate that — producing specs and user stories, and pressure-testing them the way a team would — I'd get that time back for the work that always gets squeezed out: market and competitor analysis, research, and customer usage analysis.

And it raised a bigger question. If I can impersonate every role on the team, do I still need a team at all — or just someone to orchestrate it?

1 Key Learnings

After building this, the things that matter most:

  1. It multiplies the team, it doesn't replace it. Agents make the whole team far more productive — and genuinely improve specs on a project that fits in one head. But on something as complex as an ERP, you still need people: someone has to review what the model produces and own the responsibility.
  2. The more intelligent the model, the better the specs.
  3. Specs omit details — and models can't read your mind. AI-written specs read well but quietly skip necessary details. A model can only assume what you've told it, so requirements get missed simply because they were never requested or explained. Nothing works "wonderfully and magically" if you never mentioned it.
  4. Good specs cost tokens. Producing very good specifications consumes a lot of tokens — and therefore real AI cost.
  5. Settle the framing before detailed specs. The project started as a restaurant platform and was later repositioned as an entry-level ERP, so parts of the plan had to be reworked. That wasn't the framework or the model failing — it was me changing scope and requirements, which happens in real life most of the time. Late strategy changes are expensive, even when they're right.
  6. Specs must evolve with the product. Changes are versioned and deliberate; corrections become new decisions, not edits to history.
  7. The readiness check is the cheapest bug-fix step. Finding misalignment in documents costs minutes; finding it in code costs days.
  8. Don't auto-approve. It's very tempting to just say "yes, continue" and let the agent build, commit, and test while you stay checked out. But the real work is reading, digesting, and correcting the specs before any code exists. Skipping that breeds laziness — and the fix-it-in-code loops that follow cost far more in money and time than catching it on paper.

2 Why Specs First

  • Agents drift without a single source of truth. A spec is the contract every generation must respect — prompts alone are not.
  • Traceability. Every piece of work links back to the requirement that justifies it — "why does this exist?" is answered in seconds.
  • Change control. When strategy shifts, the spec is updated deliberately instead of the codebase drifting silently.
  • Cheap errors. A mistake in a spec costs minutes to fix; the same mistake in code costs days.

Where the human sits. You don't review all 27 documents by hand — the agents cross-check each other (the review lenses read the code; the readiness check validates the PRD against architecture, UX, and epics). The human steps in at two gates only: approve the plan before build (phase 7), and accept each change against the spec (phase 10). It's orchestration, not bureaucracy.

4 What Makes a Spec Work

  • Testable acceptance criteria — written before implementation; nothing vague survives.
  • Traceability — every work item links to its requirement and the architecture decision behind it.
  • Explicit non-goals — saying what the product will not do prevents scope creep.
  • Readiness checks — plan, design, and architecture are validated against each other before any code exists.
  • Living documents — the spec evolves deliberately; changes are versioned decisions, not silent edits.

A real story — acceptance criteria

Story 1.1 — Vendor Bill Database Model & List/Detail API

As a developer, I want to create the VendorInvoice and VendorInvoiceLine
tables with list and detail API endpoints, so the data layer exists for
all downstream vendor bill features.

Acceptance Criteria:
1. Given no vendor bills exist, When I call GET /api/v1/ap/invoices,
   Then an empty list is returned
2. Given a tenant with multiple bills, When I call with a status filter,
   Then only bills matching that status are returned
3. Given a bill exists with line items, When I call GET /api/v1/ap/invoices/{id},
   Then the response includes all header fields and line items
4. Given a tenant_id is present, When any endpoint is called,
   Then data is scoped to that tenant_id via RLS
