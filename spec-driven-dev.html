Spec Driven Development

Writing the specification first — then letting AI agents implement it. The method that makes agentic coding reliable instead of chaotic.

Method: BMAD Proven on: GrandeSuite Next Status: Ongoing practice

BMAD Spec-First Traceability Agentic Delivery

AI agents can write code fast. The hard part is making sure they build the right thing — and keep building it as the product evolves. My answer: never let code lead. The spec leads; the agents follow.

Every feature starts as a written requirement with testable acceptance criteria, moves through architecture and design, and only then becomes work an agent can implement — with full traceability from code back to intent.

0 Why This Project

Agentic coding is fantastic for a personal project — you decide on the fly, change direction mid-build, and keep the whole thing in your head. But that way of working is impossible on a team. Software development has always needed structure for a reason: frameworks like Waterfall and Agile, with specifications, QA, and process, exist because coordination doesn't happen by accident.

Frameworks like BMAD caught my attention because they make that structure AI-native. With agents playing the different roles on a team — analyst, architect, designer, engineer, test architect — you can generate specifications and user stories, and even run an Agile debate without a room full of people.

As a PM, preparing user stories and running Agile ceremonies consumed about 80% of my time. If software could accelerate that — producing specs and user stories, and pressure-testing them the way a team would — I'd get that time back for the work that always gets squeezed out: market and competitor analysis, research, and customer usage analysis.

And it raised a bigger question. If I can impersonate every role on the team, do I still need a team at all — or just someone to orchestrate it?

1 Key Learnings

After building this, the things that matter most:

  1. For simple software, this is a big step forward. Agents genuinely improve specifications on a project that fits in one head. But for something as complex as an ERP, you still need people on the team — because someone has to review what the model produces. Someone needs to own the responsibility and hold the knowledge.
  2. Specs look good — but they omit details. AI-written specifications usually read well, yet they quietly skip many necessary details. Closing those gaps takes real time and iteration.
  3. It multiplies the team, it doesn't replace it. Moving 80% of my spec-writing and Agile-meeting time onto agents makes the whole team more productive — but the people, and the review they provide, are still needed.

2 Why Specs First

  • Agents drift without a single source of truth. A spec is the contract every generation must respect — prompts alone are not.
  • Traceability. Every piece of work links back to the requirement that justifies it — "why does this exist?" is answered in seconds.
  • Change control. When strategy shifts, the spec is updated deliberately instead of the codebase drifting silently.
  • Cheap errors. A mistake in a spec costs minutes to fix; the same mistake in code costs days.

4 What Makes a Spec Work

  • Testable acceptance criteria — written before implementation; nothing vague survives.
  • Traceability — every work item links to its requirement and the architecture decision behind it.
  • Explicit non-goals — saying what the product will not do prevents scope creep.
  • Readiness checks — plan, design, and architecture are validated against each other before any code exists.
  • Living documents — the spec evolves deliberately; changes are versioned decisions, not silent edits.

6 Spec-Writing Lessons

  • Settle the framing before detailed specs. The project was first planned as a restaurant platform; by the time it was repositioned as an entry-level ERP, parts of the plan had to be reworked. Late strategy changes are expensive — even when they are right.
  • Specs must evolve with the product. Changes are versioned and deliberate; corrections become new decisions, not edits to history.
  • The readiness check is the cheapest bug-fix step. Finding misalignment in documents costs minutes; finding it in code costs days.
