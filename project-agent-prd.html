AI Agent · Process

From user feedback to a PRD

A three-agent pipeline that reads raw user feedback, prioritises it against the product strategy, and drafts a reviewable product requirement — with a human approving every output.

Applied to: Worldcup Pool (developer dashboard) Status: Live Agents: 3

Multi-Agent Feedback → PRD Human Approval Gate Groq

User feedback usually dies in a backlog. This agent exists to close the loop: instead of a note nobody reads, feedback becomes a structured, prioritised product requirement that a person reviews — and only then can a coding agent pick it up.

It is a genuine multi-agent pipeline: three agents with distinct roles, chained together, with a human gate at the end. Nothing is built automatically.

1 Why This Agent

The Worldcup app already captures feedback and lets users vote on it. But votes are not a plan: someone still has to read the feedback, decide what it means, judge whether it matters against the roadmap, and write it up well enough to build.

That is exactly the kind of structured thinking an AI pipeline is good at — if it is constrained. So the agent does the analysis and the drafting, and a human keeps the decision. The pipeline turns feedback into a draft requirement; the person approves, edits, or rejects it.

2 See It in Action

The whole loop, end to end: a user submits feedback and the group upvotes it, then the agent triages it, drafts a PRD, and a person approves it.

3 The Flow

Feedback enters one end and a prioritised, reviewable PRD comes out the other — with a human gate before anything becomes work:

The approved PRDs are exposed at a dedicated endpoint that a coding agent could consume — the last step is designed, not automated.

4 The Three Agents

Strategy Owner
Analyst · classifies and prioritises
Reads the feedback, classifies its type (bug, feature, improvement, other) and assigns a priority against a six-point product strategy. If the feedback is too vague, it refuses to guess: it marks it P-PENDING and flags it as fuzzy.
PRD Writer
Author · drafts the requirement
Turns the analysis into a formal draft: title, problem statement, proposed solution, user impact, technical notes, acceptance criteria and suggested files. It only writes for P0–P2 — P3 and P-PENDING are explicitly set aside rather than forced into a requirement.
PM-Agent-Orchestrator
Orchestrator · validates and consolidates
Checks the PRD against the original feedback, resolves inconsistencies between the analysis and the draft, and consolidates everything into the final structured output. If the feedback was fuzzy, it returns a clear "needs more information" instead of a PRD.

5 The Priority Rubric

Prioritisation is not vibes. The Strategy Owner works against a fixed rubric and a product strategy, so a scoring bug outranks a nice-to-have emoji.

TierMeaningPRD written?
P0Critical bugs, scoring errors, system outagesYes
P1Core features (login, groups, scores), important bugsYes
P2Improvements to existing features, UI/UXYes
P3Minor suggestions, nice-to-haveNo — set aside
P-PENDINGAmbiguous or incomplete feedbackNo — needs clarification

The strategy the agent prioritises against covers six areas: scoring reliability, user and group growth, chat engagement, mobile UX, social features, and performance.

6 What It Produces

The final output is a single structured object, ready to be reviewed and stored:

{
  "status": "prd_generated | needs_clarification | low_priority",
  "priority": "P0 | P1 | P2 | P3 | P-PENDING",
  "title": "Implementación de Grupos Públicos con Búsqueda y Unirse",
  "problemStatement": "Los usuarios no pueden unirse a grupos existentes…",
  "proposedSolution": "Sistema de visibilidad de grupos + página de descubrimiento…",
  "userImpact": "Reduce la fricción de entrada y acelera la adopción…",
  "technicalNotes": "Modelo de grupo + endpoints de unión…",
  "acceptanceCriteria": [
    "Un admin puede marcar un grupo como Público o Privado",
    "La página de exploración lista solo grupos públicos",
    "Al pulsar Unirse, el usuario se añade sin duplicados"
  ],
  "suggestedFiles": ["models/Group.js", "routes/groupRoutes.js"]
}

The acceptance criteria are deliberately written to be testable — vague language is rejected by the PRD Writer's own instructions.

7 The Human Gate — and What's Real

Nothing is built automatically. A person reviews and approves every PRD before it becomes work. The agents analyse, draft and suggest; the decision stays with the human.

Designed in LangFlow, run in the app. The pipeline started life as a three-agent graph in LangFlow. In the product it runs those same three agents directly — a deliberate choice, mainly to avoid paying to host LangFlow around the clock for a small internal tool. LangFlow could run this in production perfectly well; it just isn't worth the extra cost here.

What that changes. Because the agents run on every request, the analysis is real rather than a stand-in — and if the model is ever unavailable, the system falls back to a simple rule-based pass instead of leaving the feedback unprocessed.

What's built: feedback capture and voting in the app, the developer dashboard, the three-agent pipeline, and the approved-PRD output a coding agent could pick up. What's not: the coding agent itself isn't wired in — the loop stops at human approval.
