AI Agents

Two very different uses of AI agents: one is a product users talk to, the other runs my own product process. They share almost nothing — which is exactly why I keep them separate.

User-facing agent: live (chatbot) Process agent: pending deployment

LangFlow Chatbot Feedback-to-PRD Human Approval Gates

Most "AI agent" work sounds the same, but there are two completely different things here. One is Agente Mundial — the personality-driven chatbot users actually talk to inside the World Cup pool app. The other is a feedback-to-PRD pipeline — a LangFlow graph that reads user feedback and turns it into a prioritized product requirement for a human to approve.

The first is a product. The second is a process. I built them separately, with different tools and different safety rules, and that separation is the point.

1 Two Agents, Two Jobs

The User-Facing Agent

What it is: Agente Mundial — a chatbot with seven distinct personalities that talks trash, summarizes matches, and answers questions in 14 languages.

Who it serves: users of the World Cup pool app.

How it works: a single stateless pipeline: memory → search → personality → LLM → judge → transcreation → response.

The Process Agent

What it is: a feedback-to-PRD pipeline — a LangFlow graph that reads raw user feedback, classifies it, and drafts a structured product requirement.

Who it serves: me, running the product.

How it works: three collaborating agents — Strategy Owner → PRD Writer → Orchestrator — with a human approving the output.

2 The User-Facing Agent — Agente Mundial

Agente Mundial is a chatbot, not a multi-agent system. Every message flows through one pipeline, with a quality gate before it reaches the user:

User Message → RAG Memory → Web Search → Personality Prompt → Groq LLM → Judge Eval → Transcreation → Response

Around that pipeline, supporting services do the agent-like work: a judge scores every response for quality and language purity; transcreation adapts humour and football idioms across 14 languages; RAG memory gives it conversation context; and web search + RSS feed it live match news.

It is deliberately one stateless chatbot plus services — simpler to debug, cheaper to run, easier to trust than a swarm of agents.

3 The Process Agent — Feedback to PRD

The second agent exists to close the loop between what users say and what gets built. Instead of feedback dying in a backlog, it becomes a reviewable, prioritized product requirement.

User Feedback → Strategy Owner → PRD Writer → Juno Orchestrator → Draft PRD → Human Approval → Coding Agent

Three agents, each with a distinct role:

  • Strategy Owner — reads the feedback and decides what it means. It classifies the type (bug, feature, improvement, other) and assigns a priority — P0 to P3, or P-PENDING when the feedback is too vague to prioritize. Crucially, it does this against a product strategy: six priorities (scoring reliability, user and group growth, chat usage, mobile UX, social features, performance) that act as its prioritization rubric. A bug in scoring outranks a nice-to-have emoji.
  • PRD Writer — turns the analysis into a formal draft requirement: title, problem statement, proposed solution, user impact, technical notes, acceptance criteria, and suggested files. It only writes PRDs for P0–P2 items; P3 and P-PENDING feedback is explicitly set aside rather than forced into a requirement.
  • Juno Orchestrator — validates and consolidates the output into the final structured PRD ready for review.

Nothing is built automatically. A human reviews and approves every PRD before it becomes work — and only then could a coding agent pick it up.

4 What's Built vs. What's Pending

The plumbing around the process agent is real and working today:

  • Feedback capture — users submit feedback (type, subject, detail) and vote on others' feedback to surface what matters most.
  • Developer dashboard — a UI to analyze feedback, generate a PRD from it, and approve, reject, or edit the draft.
  • PRD model & endpoint — approved PRDs are exposed at a dedicated endpoint that a coding agent could consume.

The LangFlow graph itself — the three agents above — is designed and exported, but not yet deployed. The integration code is in the app and calls the flow by ID; until the flow is configured on DataStax LangFlow, the app falls back to a simulated analysis (keyword-based priority) so the rest of the workflow can still be exercised.

Honest status: the feedback-to-PRD pipeline is not live in production. The agent graph exists as a LangFlow export and the surrounding workflow is built — but the LLM-driven classification is simulated until the flow is deployed.

5 Human Gates & Safety

  • PRD approval — a person approves every generated requirement before it becomes work.
  • Response review — downvotes, judge failures, and calibration signals route to a human queue, with a daily cap and deduplication.
  • Corrections — when users correct the bot, the correction is detected, logged, and fed into the review pipeline.
  • Never automatic — the agents analyze, draft, and suggest. Irreversible actions stay with people.

6 Status & Links

The user-facing chatbot is live. The process agent's workflow is built end-to-end with a simulated fallback, and the LangFlow deployment is the remaining step — import the flow, configure the flow ID, and run the full path: dashboard → analyze feedback → generate PRD → approve.
