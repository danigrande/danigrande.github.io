Agent Orchestration

AI Agents

Visual agent workflows built with LangFlow — including a feedback-to-PRD pipeline where AI reads user feedback, drafts product requirements, and hands them to a coding agent.

Tools: LangFlow · Groq · Node.js Status: Flows designed and integrated; deployment pending

I use agents for two jobs: producing the product — the chatbot users talk to — and running the product process, turning user feedback into product requirements. The second one is the more interesting experiment.

Both are built visually in LangFlow as agent graphs, exported as flow files, and called from application code by flow ID.

The User-Facing Agent

Agente Mundial — a personality-driven chatbot with conversational memory, live web search, and an automatic quality gate. Seven characters, 14 languages.

The Process Agent

A feedback-to-PRD pipeline: reads raw user feedback, triages it, and drafts a structured product requirement for human approval.

The pipeline exists to close the loop between what users say and what gets built. Instead of feedback dying in a backlog, it becomes a reviewable product requirement.

User Feedback → Strategy Owner → PRD Writer → Juno Orchestrator → Draft PRD → Human Approval → Coding Agent
  • Strategy Owner — reads the feedback and decides what kind of product decision it implies, including a priority from P0 to P3.
  • PRD Writer — turns the analysis into a draft requirement: problem statement, proposed solution, user impact, technical notes, and acceptance criteria.
  • Juno Orchestrator — coordinates the flow and produces the final structured output.

Nothing is built automatically. A human approves every PRD first — only then does a coding agent pick it up as work.

Feedback-to-PRD flow

Chat input → three collaborating agents (Strategy Owner, PRD Writer, Juno Orchestrator) → structured output ready for review.

Prediction flow

Chat input → three agents running on Groq models → match prediction output. The same visual pattern, pointed at a different job.

The integration code calls a flow by ID, sends the input, waits for the structured response, and parses it into the pipeline's data model — with a two-minute timeout and a simulation fallback when the flow isn't configured yet, so development never blocks on infrastructure.

Around the chatbot, supporting services do the agent-like work of judging quality and adapting language:

Judge

A smaller model scores every response for relevance, tone, and factuality. Low scores trigger human review.

Transcreation

Adapts every response culturally across 14 languages, preserving humour and football idioms — not literal translation.

RAG memory

Conversation history in a vector store gives the bot context, so it remembers the group and the tournament.

Web search & RSS

Live match context and breaking football news feed the responses with current information.

Deliberately not a multi-agent free-for-all. One stateless chatbot plus supporting services: simpler to debug, cheaper to run, easier to trust. Orchestration is reserved for the process work, where the LangFlow graphs earn their keep.

  • PRD approval — a person approves every generated requirement before it becomes work.
  • Response review — downvotes, judge failures, and calibration signals route to a human queue, with a daily cap and deduplication.
  • Corrections — when users correct the bot, the correction is detected, logged, and fed into the review pipeline.
  • Never automatic — the agents analyze, draft, and suggest. Irreversible actions stay with people.

The flows are exported, the integration code is in the app, and the deployment path is documented. Remaining: import the flow into DataStax LangFlow, configure the API key and flow ID in the environment, then run the end-to-end test — dashboard → analyze feedback → generate PRD → approve.

Pending: the feedback-to-PRD pipeline is not yet live in production. Until then, the app falls back to a simulated analysis path so the rest of the workflow can still be exercised.
